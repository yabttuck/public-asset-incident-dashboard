## 1. 서비스 개요

### 1.1 서비스명 및 컨셉

| 항목 | 내용 |
|---|---|
| 서비스명 | 공공 시설물·전산 자산 장애 접수 및 관제 대시보드 |
| 한 줄 설명 | 공공기관의 장애 신고부터 조치 이력과 처리 기한까지 한곳에서 확인하는 운영 웹 서비스 |
| 서비스 유형 | 내부 업무용 웹 대시보드 |
| 목표 플랫폼 | 반응형 웹 |
| 예정 기술 | Next.js, TypeScript, Supabase |

서비스는 서버·네트워크 장비와 공공 시설물의 이상 신고를 표준 형식으로 수집한다. 운영 담당자는 우선순위와 담당자, 처리 기한을 정하고 접수·조치 중·완료 과정을 기록한다. 신고자는 본인 신고의 진행 상황을 확인한다.

#### 사용자 문제와 근거

현재 저장소에는 기관 인터뷰, 현행 처리시간, 장애 통계 등 실증 자료가 없다. 따라서 아래 내용은 공공기관 업무 흐름에 근거한 **기획 가설**이며, 실제 적용 기관이나 사용자 인터뷰로 검증해야 한다.

| 문제 ID | 사용자·상황·문제 가설 | 현재 대안과 한계 가설 | 확인 근거/상태 | 다음 검증 |
|---|---|---|---|---|
| OBJ-001 | 신고자가 담당자와 처리 상태를 알기 어렵다 | 전화·메신저 문의가 반복될 수 있다 | 미검증 가설 | 담당자 인터뷰, 신고자 여정 확인 |
| OBJ-002 | 담당자가 여러 채널의 요청을 한눈에 비교하기 어렵다 | 수기 목록은 담당자·기한 누락 위험이 있다 | 미검증 가설 | 현행 접수 양식과 처리대장 조사 |
| OBJ-003 | 변경 이유와 처리 과정이 분산될 수 있다 | 사후 회고·인수인계가 어려워질 수 있다 | 미검증 가설 | 감사·인수인계 요구사항 확인 |

### 1.2 핵심 가치 제안

| 항목 | 내용 |
|---|---|
| 핵심 가치 | 장애를 접수부터 완료까지 추적해 미처리와 기한 위험을 빠르게 드러낸다 |
| 사용자 이점 | 신고자는 진행 상태를 직접 확인하고 운영자는 담당·기한·이력을 한 화면에서 관리한다 |
| 차별화 방향 | 상태 및 감사 이력, 역할별 접근 제어, 자산과 신고 연결을 업무 흐름에 맞춰 제공 |
| 가치 검증 조건 | 사용자가 신고 추적과 인수인계에 실제 도움이 된다고 평가하는지 파일럿에서 확인 |

### 1.3 타겟 사용자 정의

#### 주요 사용자 페르소나

**신고자 — 현장 직원 또는 내부 사용자**
- 시설·전산 자산의 장애를 발견하고 정확한 담당 부서를 모를 수 있다.
- 필요한 자산·위치·증상 정보를 빠르게 입력하고 접수 여부와 처리 상황을 알고 싶다.
- 다른 부서 신고, 내부 메모, 민감한 자산 세부정보는 볼 필요가 없다.

**운영 담당자 — 전산실 또는 시설 관리 담당자**
- 여러 접수 건의 우선순위, 담당자, 처리 기한을 정하고 조치 이력을 남긴다.
- 현재 미처리·기한 임박·초과 건을 빠르게 찾고 누락을 줄이고 싶다.

**관리자 — 업무 시스템 관리자**
- 내부 사용자 역할과 자산 목록을 관리하고, 운영 기준 변경의 책임과 이력을 관리한다.

#### 사용자 세그먼트

- 전산 자산 운영: 서버, 네트워크, 업무용 장비 장애
- 공공 시설 운영: 건물·설비·공용 시설의 장애 및 현장 조치
- 관리 책임자: 처리 현황, SLA 준수, 유형별 추이 확인

기관별 용어와 우선순위 체계는 도입 전 설정이 필요하다.

#### 비사용자 (Anti-Persona)

- 외부 일반 시민을 대상으로 한 공개 민원·신고 포털 이용자
- 실제 운영 환경의 계정 없이 임의로 전체 신고 데이터를 조회하려는 사용자
- 자동 설비 모니터링 시스템을 대체하려는 사용자

공개 신고 포털과 자동 장애 감지는 v1 범위가 아니다.

## 2. 핵심 메커니즘

### 2.1 서비스 작동 원리

1. 신고자가 로그인해 자산 또는 위치와 증상을 제출한다.
2. 시스템이 필수값을 검증하고 같은 자산의 미해결 유사 신고를 안내한다.
3. 운영 담당자가 신고를 분류하고 담당자와 기한을 지정한다.
4. 처리 단계와 공개 조치 요약, 내부 메모를 구분해 기록한다.
5. 대시보드는 상태별 건수와 SLA 위험을 집계하고 신고자는 본인 건을 확인한다.

### 2.2 전체 서비스 플로우

`발견 → 로그인 → 신고 작성 → 중복 의심 확인 → 접수 → 분류·배정 → 조치 중 → 완료 → 이력 및 통계 조회`

사용자는 상태를 확인하기 위해 매번 운영 담당자에게 별도 문의하지 않아도 된다. 운영 담당자는 한 목록에서 우선 대응 건을 고르고 상세 기록을 누적한다.

### 2.3 핵심 사용자 여정

#### 여정 1: 장애 신고 및 진행 확인

신고자가 장애를 발견하고 로그인한다. 자산·위치와 증상을 입력하고, 미해결 유사 건 안내를 검토한다. 접수 후 ID와 초기 상태를 확인하고, 이후 본인 신고 목록에서 공개된 진행 상태와 조치 요약을 확인한다.

**성공 조건:** 필수 정보가 저장되고 신고 ID가 발급되며, 타인의 신고 정보가 노출되지 않는다.

#### 여정 2: 운영 담당자의 분류 및 처리

담당자가 미처리 목록에서 신고를 연다. 자산과 증상을 확인하고 우선순위, 담당자, 처리 기한을 설정한다. 조치 중으로 변경하고 기록을 추가한 뒤 결과 요약과 함께 완료한다.

**성공 조건:** 변경 책임과 시각이 기록되고, 상태 변경과 감사 이력이 함께 저장된다.

## 3. 기능 전략

### 3.1 핵심 기능 방향

- **접수:** 구조화된 신고 폼, 자산 선택, 미해결 유사 신고 안내
- **관제:** 상태별 요약 카드, 기간별 추이, 필터·정렬 가능한 신고 목록
- **처리:** 우선순위·담당자·기한 지정, 조치 메모, 상태 변경 이력
- **권한:** 신고자·운영 담당자·관리자의 데이터 및 행동 분리
- **정보 신뢰:** 기한 초과 계산과 변경 이력 누락 방지

### 3.2 진행·보상 구조

게이미피케이션, 점수, 신고 건수 보상은 도입하지 않는다. 업무상 공정성과 정확한 기록을 위해 속도 경쟁이나 신고량 보상보다 처리 책임과 품질을 강조한다.

### 3.3 콘텐츠 전략

일반 콘텐츠 피드 대신 업무 데이터를 제공한다. 신고 상세에는 요약, 자산/위치, 우선순위, 상태, 담당자, 기한, 공개 조치 요약을 표시한다. 내부 메모와 개인 정보는 신고자 화면에 노출하지 않는다.

### 3.4 브랜드·톤앤매너

- 차분하고 명료한 공공 업무용 표현을 사용한다.
- 오류는 문제 원인과 사용자가 할 수 있는 다음 행동을 안내한다.
- 긴급·초과 상태를 분명하게 표시하되 불필요한 경고 문구나 과장된 색을 피한다.
- 화면 위계와 컴포넌트 표현은 DESIGN.md를 따른다.

## 4. 운영·수익 모델

### 4.1 수익 모델

본 프로젝트는 취업 포트폴리오와 교육용 MVP로 기획하며 상업적 수익화를 목표로 하지 않는다. 결제, 구독, 광고, 유료 콘텐츠 기능은 만들지 않는다.

### 4.2 운영 모델

초기에는 한 기관 또는 단일 운영 조직의 내부 시범 운영을 가정한다. 실제 도입 시 계정 발급, 데이터 소유·보존, SLA, 지원 책임과 운영 시간은 해당 기관의 승인으로 정한다.

### 4.3 운영 정책 요약

역할, 상태 전이, 기한 계산, 중복 의심, 통계 기준은 비즈니스정책서.md를 기준으로 한다. 실제 기관 정책이 확인되기 전에는 제안 기본값을 운영 규정처럼 표현하지 않는다.

## 5. MVP 범위

### 5.1 MVP 정의 기준

핵심 업무 흐름인 신고 접수 → 담당자 분류 → 조치 기록 → 완료 → 진행 상황 확인을 한 사용자가 끝까지 수행할 수 있어야 한다. 보안과 감사 이력은 핵심 기능의 일부이므로 MVP에서 제외하지 않는다.

### 5.2 포함 항목 (In-Scope)

- 로그인과 세 가지 역할(신고자, 운영 담당자, 관리자)
- 자산 기본 목록 및 장애 신고 생성
- 중복 의심 알림과 신고 ID 발급
- 담당자·우선순위·처리 기한 지정
- 접수·조치 중·완료 상태와 감사 이력
- 신고자 공개 처리 요약과 관리자 내부 메모
- KPI 카드, 신고 목록, 검색·필터·정렬
- SLA 임박·초과 표시 및 빈 화면·오류 피드백
- 역할별 RLS 기반 접근 통제와 반응형 레이아웃

### 5.3 제외 항목 (Out-of-Scope)

| 항목 | 제외 근거 |
|---|---|
| 공개 시민 신고 포털 | 내부 사용자 중심 MVP 가정이며 개인정보·민원 운영 정책 미정 |
| 문자·이메일·푸시 알림 | 수신 동의, 발송·실패·재시도 정책이 미정 |
| 자동 설비 탐지 및 IoT 연동 | 연동 대상·프로토콜·운영 환경 미정 |
| 휴일·근무시간을 반영한 SLA | 기관별 근무일 및 서비스 수준 정책 미정 |
| 사진·문서 첨부 | 형식, 용량, 악성 파일 검사, 보존 정책이 미정. 후속 단계 검토 |
| 자동 신고 병합·자동 담당 배정 | 오분류 위험을 줄이고 운영 규칙을 검증한 뒤 검토 |
| 과금, 광고, 게이미피케이션 | 프로젝트 목적과 무관 |

### 5.4 MVP 기능 흐름

`인증/역할 → 신고 작성 → 유사 신고 안내 → 접수 목록 → 담당자 배정 및 기한 지정 → 상태/조치 이력 → 완료/신고자 확인`

### 5.5 기술적 MVP 결정사항

- 예정 스택은 Next.js, TypeScript, Supabase Auth/Postgres다.
- Supabase RLS를 권한 강제 지점으로 삼는다.
- 상태 변경과 감사 이력 기록은 원자적으로 성공 또는 실패해야 한다.
- 환경·계정·배포 방식은 코드베이스 생성 후 세부 설계에서 확정한다.

## 6. KPI 가설 검증 프레임워크

### 6.1 검증 가설

| 가설 ID | 가설 | 확인 방법 |
|---|---|---|
| H-01 | 단일 접수 목록은 미처리 현황 파악 시간을 줄인다 | 사용자 과업 관찰 및 미처리 검색 시간 비교 |
| H-02 | 신고자 상태 조회는 진행 상황 문의를 줄인다 | 파일럿 전후 문의 건수 비교 |
| H-03 | 기한·우선순위 시각화는 SLA 초과 건을 조기에 식별하게 한다 | 기한 초과율과 임박 건 대응 여부 확인 |
| H-04 | 자동 감사 이력은 인수인계와 사후 확인을 쉽게 한다 | 담당자 인터뷰와 이력 조회 과업 평가 |

### 6.2 핵심 지표

- 운영 효율: 배정까지 걸린 중앙 시간, 완료까지 걸린 중앙 시간
- 처리 관리: 기한 임박/초과 건수, 미처리 건의 평균 경과 시간
- 신고자 경험: 본인 신고 상태 확인 성공률, 진행 문의량
- 데이터 품질: 필수 필드 누락률, 감사 이력 누락률, 중복 의심 안내 후 처리 결과
- 보안: 권한 테스트 통과율, 권한 오류 건수

수치 목표는 실제 업무 기준선 없이 임의로 정하지 않는다.

### 6.3 검증 매트릭스

| 대상 | 데이터 | 수집 시점 | 주의사항 |
|---|---|---|---|
| 신고자 | 신고 완료율, 상태 확인 과업 성공 | 사용성 검증 | 개인 식별정보 최소화 |
| 운영 담당자 | 배정·완료 시간, 기한 관리 | 파일럿 기간 | 조직 업무량 차이를 함께 해석 |
| 관리자 | 권한 오류, 이력 누락, SLA 집계 | 파일럿/검토 | 테스트 계정과 실제 사용자 구분 |

### 6.4 데이터 수집 계획

집계에 필요한 이벤트만 기록한다. 사용자 행동 분석을 추가할 경우 목적, 보존 기간, 접근 권한과 기관 개인정보 정책을 먼저 확인한다. 테스트에는 가상 자산과 가상 신고만 사용한다.
