## 1. 문서 개요

### 1.1 목적

신고 접수, 접근 권한, 상태 변경, 기한 계산, 이력 및 통계가 화면이나 담당자에 따라 달라지지 않도록 공통 규칙을 정한다. 개발과 검증은 이 문서를 PRD와 함께 참고한다.

### 1.2 작성 원칙

각 정책은 목적, 규칙, 상황별 예시를 제공한다. 기관별 SLA 수치, 계정 발급, 파일 보존 기간 등 근거가 없는 값은 임의 확정하지 않고 13장 미결정 항목으로 관리한다.

### 1.3 관련 문서

- [PRD.md](../../PRD.md): 목표, 범위, 기능 및 수용 기준
- [DESIGN.md](../../DESIGN.md): 화면 및 상호작용 설계 기준

## 3. 인증·권한 정책

### BP-AUTH-001: 로그인과 계정 사용

**목적:** 신고 및 운영 이력을 사용자 계정과 연결하고 비인가 접근을 막는다.

**규칙**
- 신고 목록과 상세는 인증된 사용자만 접근할 수 있다.
- v1은 공개 익명 신고를 제공하지 않는다.
- 사용자 초대, 계정 생성, 비밀번호 복구 절차는 기관의 계정 운영 방식이 결정된 뒤 확정한다. 예상 기술은 Supabase Auth다.

**예시:** 로그인하지 않은 사용자가 신고 URL을 열면 데이터 대신 로그인 화면을 본다.

### BP-AUTH-002: 역할 및 권한

**목적:** 신고자의 개인정보와 내부 운영 정보를 보호한다.

**규칙**
- 신고자는 신고를 생성하고 본인이 제출한 신고 및 신고자 공개 상태·처리 요약만 조회한다.
- 운영 담당자는 전체 신고, 배정, 우선순위, 기한, 상태 및 조치 내용을 관리한다.
- 관리자는 운영 담당자 권한과 사용자 역할·자산·운영 기준 관리 권한을 가진다.
- 역할 검증은 서버와 데이터베이스 RLS에서 시행한다. UI 제어만으로 접근을 허용하지 않는다.
- 역할 변경 이력은 관리자와 변경 시각을 기록한다.

**예시:** 신고자가 다른 신고 ID를 추측해 상세를 요청해도 해당 데이터는 반환하지 않는다.

### BP-AUTH-003: 내부 메모 접근

**규칙:** 내부 메모는 운영 담당자와 관리자만 조회한다. 신고자에게 보여줄 처리 요약과 내부 메모는 별도 필드와 권한으로 관리한다.

**예시:** 담당자가 장애 원인 분석 메모를 기록해도 신고자는 공개 처리 요약만 볼 수 있다.

## 4. 과금·콘텐츠·광고 정책

### BP-COMM-001: 상업 기능 비적용

**규칙:** 본 프로젝트는 교육·포트폴리오용 업무 시스템이며 결제, 유료 플랜, 광고, 콘텐츠 해금, 구독을 제공하지 않는다. 사용량을 결제와 연결하거나 광고성 메시지를 표시하지 않는다.

**예시:** 자산 수나 신고 건수가 늘어도 결제 절차나 광고가 표시되지 않는다.

## 5. 알림 정책

### BP-NOTI-001: MVP 알림 범위

**목적:** 신고자가 현재 처리 단계를 확인할 수 있게 한다.

**규칙**
- MVP는 서비스 내 신고 상태와 처리 요약을 기준 정보로 제공한다.
- 이메일, 문자, 모바일 푸시 발송은 구현 범위에서 제외한다.
- 알림 채널을 추가하기 전 수신 대상, 동의, 개인정보, 발송 실패 및 재시도 정책을 별도로 승인한다.

**예시:** 상태가 변경되면 신고 상세에서 최신 상태와 변경 시각을 확인할 수 있지만 외부 문자 발송을 보장하지 않는다.

## 6. 날짜·데이터 리셋 정책

### BP-DATA-001: 시각 저장과 표시

**규칙**
- 접수, 상태 변경, 조치 기록은 서버 기준 시각을 저장한다.
- 사용자 화면은 Asia/Seoul 기준으로 표시한다.
- 기간 필터의 시작일과 종료일은 사용자에게 보이는 한국 날짜를 기준으로 포함 범위를 명확히 적용한다.

**예시:** 한국 시간으로 11월 24일에 제출한 신고는 화면에 11월 24일로 표시한다.

### BP-DATA-002: 리셋·삭제

**규칙**
- 운영 데이터에 자동 초기화나 정기 삭제를 적용하지 않는다.
- 일반 사용자는 신고와 감사 이력을 삭제할 수 없다.
- 보존 기간과 개인정보 파기 절차는 기관 정책 확인 전까지 미정이며, 프로덕션 데이터 적용 전에 승인받는다.
- 테스트 데이터는 실제 개인정보를 사용하지 않는다.

**예시:** 완료 신고도 대시보드의 미처리 수에서는 제외하지만 이력에서 임의 삭제하지 않는다.

## 7. 오류·재시도 정책

### BP-ERR-001: 저장 및 네트워크 오류

**규칙**
- 저장이 확인되기 전 성공으로 표시하지 않는다.
- 실패 시 사용자가 입력한 폼 값을 가능한 범위에서 유지하고 재시도할 수 있게 한다.
- 중복 요청으로 신고가 두 번 생성되지 않도록 요청 식별 또는 서버 검증을 적용한다.
- 오류 메시지는 사용자에게 다음 행동을 안내하고 내부 오류 세부정보·비밀 키를 노출하지 않는다.

**예시:** 신고 저장 요청이 시간 초과되면 성공 화면으로 이동하지 않고 재시도 안내와 입력값을 유지한다.

### BP-ERR-002: 동시 변경과 이력 저장 실패

**규칙**
- 저장 시점의 현재 상태를 확인한다. 다른 담당자가 먼저 상태를 변경했다면 최신 상태를 보여주고 사용자가 다시 확인하도록 한다.
- 상태 변경과 감사 이력 기록은 하나의 일관된 성공/실패 단위다. 이력 저장 실패 시 상태 변경도 반영하지 않는다.

**예시:** 상태가 이미 완료로 바뀐 신고를 조치 중으로 덮어쓰지 않고 최신 상태를 안내한다.

## 8. 통계·카운팅 정책

### BP-STAT-001: 상태별 카운트

**규칙**
- 전체 접수는 선택된 기간·검색·자산 필터에 포함되는 신고 수다.
- 미처리는 완료가 아닌 신고 수다.
- 완료는 현재 상태가 완료인 신고 수다.
- SLA 초과는 처리 기한이 지났고 현재 완료 상태가 아닌 신고 수다.
- 중복 의심 안내 건은 별도 신고 레코드이므로 접수 건수에 포함한다.

**예시:** 기한을 넘긴 뒤 완료된 신고는 전체·완료에는 포함하고 현재 SLA 초과 건에는 포함하지 않는다.

### BP-STAT-002: 기본 기간과 갱신

**규칙**
- 카드, 표, 차트는 동일한 활성 필터 조건을 적용한다. 다만 상태별 카드의 정의는 BP-STAT-001을 따른다.
- 대시보드 기본 조회 기간은 최근 30일을 제안값으로 사용한다. 기관 검토 전에는 이 값을 운영 정책으로 간주하지 않는다.
- 화면에는 데이터 갱신 시각을 표시한다. 자동 새로고침 주기는 구현 시 정하고 표시한다.

**예시:** 최근 30일 필터가 설정되어 있으면 카드와 표가 같은 기간을 기준으로 집계된다.

## 9. 장애 접수 및 중복 의심 정책

### BP-INC-001: 필수 접수 정보

**규칙**
- 필수 입력은 자산 또는 발생 위치, 제목, 상세 증상, 우선순위, 발생 시각이다.
- 접수 ID, 신고자, 접수 시각, 초기 상태 접수는 시스템이 생성한다.
- 자산 목록에서 선택할 수 없는 위치도 신고할 수 있도록 원문 위치를 보존한다.

**예시:** 제목이 비어 있으면 저장하지 않고 해당 필드의 오류를 표시한다.

### BP-INC-002: 중복 의심

**규칙**
- 같은 자산에 미해결 신고가 있으면 유사 신고 목록과 접수 ID를 보여준다.
- 자동 병합 및 접수 차단은 하지 않는다. 별개의 증상일 수 있으므로 신고자가 새 신고를 계속할 수 있다.
- 운영 담당자는 검토 후 관련 신고를 참조할 수 있다. 신고 삭제나 합치기는 MVP에서 제공하지 않는다.

**예시:** 같은 서버에 장애 신고가 열린 상태라도 다른 장애 증상이라면 새 건으로 등록할 수 있다.

## 10. 처리·SLA 정책

### BP-OPS-001: 우선순위 지정

**규칙:** 신고자는 우선순위를 제안하고 운영 담당자는 검토 후 확정하거나 변경할 수 있다. 등급 이름과 심각도 기준은 기관 정책이 확정될 때까지 프로젝트 제안값으로만 관리한다. 변경자는 감사 이력에 기록한다.

**예시:** 신고자가 긴급으로 표시했으나 담당자가 일반으로 조정하면 변경 사유를 기록하고 현재 우선순위를 명확히 보여준다.

### BP-OPS-002: 상태 전이

**규칙**
- 정상 흐름은 `접수 → 조치 중 → 완료`다.
- 완료는 결과 요약을 입력한 뒤에만 가능하다.
- 완료 신고는 직접 재개하지 않는다. 추가 조치가 필요하면 기존 신고 ID를 참조하는 후속 신고를 만든다.
- 관리자 정정은 사유와 함께 기록한다.

**예시:** 결과 요약 없이 완료를 선택하면 상태를 바꾸지 않고 누락 항목을 안내한다.

### BP-OPS-003: 자산 비활성화

**규칙:** 비활성 자산은 신규 신고 대상 선택에서 제외하되 과거 신고의 자산 표시는 유지한다. 자산 삭제는 참조된 신고 이력을 끊으므로 MVP에서 제공하지 않는다.

**예시:** 폐기 자산은 신규 선택 목록에 나오지 않아도 과거 장애 상세에서 식별 가능하다.

### BP-SLA-001: 처리 기한

**규칙**
- 운영 담당자는 신고별 처리 기한을 지정한다.
- 기관 SLA 시간은 미확정이다. 자동으로 우선순위별 법정/기관 기한을 가정하지 않는다.
- 휴일·근무시간 제외 계산은 v1에서 하지 않는다.

**예시:** 담당자가 금요일 17시를 기한으로 지정하면 시스템은 해당 시각을 기준으로 경과 여부를 계산하며 주말 자동 연장은 하지 않는다.

### BP-SLA-002: 임박·초과 표시

**규칙**
- 현재 시각이 처리 기한을 넘고 상태가 완료가 아니면 SLA 초과로 표시한다.
- 임박 기준은 관리자 설정값으로 둔다. 초기값이 필요하면 남은 시간 24시간 이하를 제안값으로 사용한다.
- 기한이 지정되지 않은 신고는 임박 또는 초과로 집계하지 않고 기한 미지정으로 구분한다.

**예시:** 기한이 내일 16시이고 임박 기준이 24시간이면 임박으로 표시한다. 기한 미지정 건은 초과 수에 포함하지 않는다.

## 11. 감사 이력·정보 공개 정책

### BP-AUDIT-001: 감사 이력 보존

**규칙:** 신고 생성, 배정, 우선순위·기한·상태 변경, 공개 처리 요약 수정, 관리자 정정에 대해 행위자, 시각, 항목, 이전 값, 새 값을 기록한다. 감사 이력은 일반 UI에서 수정·삭제할 수 없다. 상태와 이력은 같은 트랜잭션에서 저장한다.

**예시:** 담당자 변경은 이전 담당자, 새 담당자, 변경한 사용자와 시각을 남긴다.

### BP-PRIV-001: 공개 처리 요약과 내부 메모

**규칙:** 신고자에게 제공되는 조치 요약과 내부 메모는 별도로 관리한다. 신고자에게 공개되는 정보에는 다른 사용자의 개인정보나 보안상 민감한 세부 내용을 포함하지 않는다.

**예시:** 내부 원인 분석 로그는 담당자에게만 보이고, 신고자에게는 복구 여부와 안내 사항을 요약해 제공한다.

## 12. MVP 정책 적용 범위

### 적용

BP-AUTH-001`003, BP-DATA-001`002, BP-ERR-001`002, BP-STAT-001, BP-INC-001`002, BP-OPS-001`003, BP-SLA-001`002, BP-AUDIT-001, BP-PRIV-001을 적용한다.

### MVP에서 제외

- 결제·구독·광고·콘텐츠 해금
- 문자·이메일·푸시 알림
- 자동 장애 감지 및 설비 연동
- 자동 신고 병합 및 삭제
- 휴일·근무시간 기반 SLA 계산
- 승인되지 않은 보존 기간에 따른 자동 파기

## 13. 정책 변경 관리

### 13.1 변경 절차

변경 제안은 정책 ID, 사유, 영향받는 역할·화면·데이터, 테스트 항목을 함께 기록한다. 개인정보, 권한, 이력, SLA 정책 변경은 구현 전 검토·승인한다. 승인된 변경은 이 문서와 PRD를 함께 갱신한다.

### 13.2 미결정 항목

| 항목 | 현재 상태 | 기본 제안 | 확정 담당 |
|---|---|---|---|
| 계정 발급과 사용자 유형 | 미정 | 내부 계정 초대 방식 | 기관 운영 담당 |
| SLA 기준과 등급별 기한 | 미정 | 건별 수동 설정 | 업무 책임자 |
| SLA 임박 기준 | 미정 | 24시간 이내 | 업무 책임자 |
| 우선순위 단계 | 미정 | 운영 담당자가 단계 확정 | 업무 책임자 |
| 파일 형식·용량·보존 기간 | 미정 | 파일 기능은 P1로 보류 | 보안·운영 담당 |
| 데이터 보존·파기 | 미정 | 자동 삭제 없음 | 개인정보/기록 담당 |

## 14. 용어 정의

| 용어 | 정의 |
|---|---|
| 신고자 | 장애를 등록하고 본인 신고의 공개 상태를 확인하는 사용자 |
| 운영 담당자 | 신고를 분류하고 담당자·기한·상태를 관리하는 사용자 |
| 관리자 | 사용자 역할, 자산, 운영 기준을 관리하는 사용자 |
| 처리 기한 | 운영 담당자가 신고 건에 지정한 완료 목표 시각 |
| SLA 초과 | 기한이 지났으며 아직 완료되지 않은 신고 |
| 감사 이력 | 누가 언제 어떤 업무 데이터를 변경했는지 기록한 불변 이력 |
