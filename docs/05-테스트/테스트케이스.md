# 테스트 케이스 문서 (Test Cases)

## 1. 관리 규칙
케이스 ID는 영역별 고유 번호로 관리한다. 사전 조건과 테스트 데이터가 준비된 뒤 실행하며 결과는 미실행, 통과, 실패, 차단 중 하나로 기록한다. 실패에는 결함 ID와 증빙을 연결한다. 현재 모든 케이스는 계획 상태이며 실행 결과가 아니다.

성능 목표와 지원 브라우저는 미확정이다. 숫자 기준을 임의로 넣지 않으며 운영 요구 확정 후 별도 성능·호환성 케이스를 추가한다.

## 4. UX 시나리오
1. 신고자가 장애를 입력하고 유사 신고 안내를 확인한 뒤 접수하고 접수 ID를 확인한다.
2. 운영 담당자가 미처리 신고를 검색해 담당자와 기한을 설정하고 공개 업데이트를 남긴다.
3. 운영 담당자가 결과 요약을 입력해 완료하고 신고자 계정으로 공개 상태를 확인한다.
4. 사용자가 필터 오류 또는 네트워크 오류 상황에서 입력을 잃지 않고 복구한다.

측정은 완료 여부, 잘못된 입력 수, 도움 요청 및 사용자 의견을 기록한다. 사용성 참여자와 표본 수는 섭외·승인 전까지 미정이다.

## 5. 회귀 기준
신고·인가·상태·감사·SLA 핵심 케이스(TC-RBAC-01~03, TC-INC-01, TC-DUP-01, TC-AUDIT-01~02, TC-STATUS-01~02, TC-SLA-01~03)는 관련 코드나 RLS/DB 마이그레이션 변경 때 재실행한다. 실패를 무시한 채 회귀 통과로 보고하지 않는다.

## 6. 결함 보고 템플릿
- 결함 ID / 제목 / 심각도 / 우선순위
- 대상 빌드·브라우저·역할·환경
- 재현 단계와 테스트 데이터(비식별)
- 기대 결과 / 실제 결과
- 증빙 링크 / 관련 FR·TC
- 수정 상태 / 수정 버전 / 재검증 결과

새 케이스를 추가할 때 SRS 요구사항, 역할, 사전 조건, 기대 결과, 데이터 정리 방법을 검토한다.
