## 4. 성능·보안·UX 결과
성능 수치, 동시 사용자 수, 부하 결과는 측정하지 않았다. 응답 시간·가용성 목표도 기관 요구 미확정으로 설정되지 않았다. RLS, 키보드 접근성, 전체 반응형 흐름, 사용성 점검은 미실행이므로 적합 판정을 내리지 않는다. 구현 후 [테스트 계획서](테스트계획서.md)의 환경 및 절차에 따라 측정 결과와 증빙을 추가한다.

- 코드 커버리지: 수집 도구를 구성하지 않아 측정하지 않음.
- 테스트 케이스 정의와 실행 완료를 구분해 보고한다. 문서상 매핑은 구현 검증 완료를 의미하지 않는다.

## 6. 종료 기준 판정
G5 출시 종료 기준은 충족되지 않았다. P0 요구사항의 테스트 통과, S1/S2 결함 해소, 권한·감사·완료 흐름 검증, UAT 승인 및 기관 미결정 정책 확인을 완료한 뒤 재평가한다. 정적 코드 검증의 통과만으로 기능 인수나 배포 준비 완료를 선언하지 않는다.

## 7. 잔여 위험 및 권고
- 권한 정책이 DB RLS에서 검증되기 전에는 실제 사용자 데이터를 투입하지 않는다.
- 상태 변경과 감사 로그가 원자적으로 저장되는 통합 테스트를 배포 전에 수행한다.

### 정책·제품 확인 항목

- **중복 신고 정보:** RPC는 선택한 활성 자산의 미해결 신고 번호·상태·접수일을 신고자에게 반환한다. 제목·상세는 반환하지 않는다. 다른 신고자의 접수 메타정보 노출이 기관 정책에 맞는지 승인받아야 한다.
- **우선순위 검증:** DB 함수는 우선순위가 비어 있지 않은지와 길이를 검사하지만 허용값 집합을 DB에서 제한하지 않는다. 허용 등급이 확정되면 제약 또는 RPC 허용목록 검증을 추가한다.
- **랜딩 문구:** 공개 첫 화면은 “서비스 개발 준비”, “기반 구축 중”이라고 안내하면서 로그인 가능한 업무 화면을 제공한다. 공개 목적이 데모인지 서비스 소개인지에 맞춰 문구를 정리한다.

### 데이터베이스 검증 한계

저장소의 마이그레이션 SQL에서는 직접 테이블 변경 권한을 제한하고, 상태·배정 RPC가 역할과 예상 버전을 확인하며 감사 기록을 같은 트랜잭션에서 남기도록 정의한 것을 읽기 전용으로 확인했다. 실제 Supabase에 적용된 정책·권한·함수 정의 및 두 신고자 간 격리는 확인하지 않았다. 이 항목들은 SQL 정의 검토를 통과한 것으로만 기록하며, 통합 검증은 미실행이다.
