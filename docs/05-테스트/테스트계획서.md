## 문서 개요
- 제품: 공공 시설물·전산 자산 장애 접수 및 관제 대시보드
- 버전/상태: 0.1 / 초안
- 작성일: 2026-11-24
- 기준 문서: [SRS](../01-요구사항분석/요구사항명세서-SRS.md), [RTM](../01-요구사항분석/요구사항추적매트릭스-RTM.md), [상세 설계](../03-상세설계/상세설계서.md)
- 현재 상태: 앱 코드 구현. 전용 테스트 러너와 Supabase 검증 프로젝트/역할 계정은 아직 없어 업무 케이스 실행 대기

## 1. 목적과 범위

테스트 목적은 장애 접수부터 완료까지 요구사항과 권한을 확인하고, 상태·감사 이력의 일관성 및 개인정보 보호를 검증하는 것이다. 이 문서는 검증 접근과 진입/종료 조건을 정의하며 실제 결과는 테스트 결과 보고서에 기록한다.

### 포함 범위
인증 및 역할 접근, 자산 관리, 신고 입력·유사 신고 안내, 신고 목록·검색, 배정·기한, 공개 업데이트·내부 메모, 상태 변경·완료, 감사 원자성, SLA 집계, 반응형·접근성·오류 상태를 포함한다. P1 첨부·분석·CSV는 구현 승인 이후 별도 범위로 검증한다.

### 제외 범위
시민 대상 공개 신고, 자동 설비 탐지, 이메일·문자 알림, 휴일·근무시간 SLA, 실제 기관 성능·가용성 인증은 제외한다. 계정 발급 방식·기관 SLA 등 미확정 정책은 합의 전 확정 기대값으로 테스트하지 않는다.

## 2. 테스트 전략

| 수준 | 접근 |
|---|---|
| 단위 | 필드 검증, 상태 전이, SLA 경계값, 오류 변환을 격리 검증 |
| 통합 | Supabase Auth/RLS, DB 함수·제약, 상태와 감사 로그 트랜잭션 검증 |
| 시스템 | 역할별 주요 화면 흐름과 로딩·오류·빈 상태 점검 |
| 인수(UAT) | 신고자·운영 담당자·관리자가 승인된 업무 시나리오를 수행 |

기능은 [테스트케이스.md](테스트케이스.md)의 ID로 기록한다. TDD 적용 시 중복 요청, 상태 전이, 감사 이력 실패 테스트를 먼저 작성하고 구현한다.

## 3. 환경 및 데이터

앱 코드는 로컬에서 정적 검증할 수 있으나 Supabase 개발/검증 환경은 미구성 (`.env.local`, Supabase CLI, Docker 없음). 실제 연동 전에 별도 프로젝트를 사용하고 운영 데이터를 복사하지 않는다. 테스트 계정은 역할별로 별도 생성한다: 신고자 A/B, 운영 담당자, 관리자, 비활성 사용자. 테스트 자산과 신고는 가짜 값으로 구성한다. 모든 테스트가 끝난 뒤 데이터 초기화 방법을 기록한다. 비밀값은 문서·저장소에 저장하지 않는다.

현재 `package.json`에는 `test` 스크립트나 테스트 프레임워크가 없다. 타입 검사·린트·production build는 코드 품질 확인이며 테스트 케이스 실행 결과로 간주하지 않는다. 자동화 프레임워크 선택과 DB 테스트 환경이 준비되면 단위·통합 케이스 실행을 별도 기록한다.

브라우저 지원 범위와 자동화 도구는 프로젝트 구현 후 결정한다. 수동 UI 확인과 자동화 테스트 결과는 구분해서 보고한다.

## 4. 진입·종료 기준

| 단계 | 진입 조건 | 종료 조건 |
|---|---|---|
| 단위 | 기능 코드·테스트 러너 존재 | 핵심 업무 규칙 테스트 통과 |
| 통합 | 마이그레이션과 테스트 DB 준비 | RLS, 트랜잭션, 제약 시나리오 통과 |
| 시스템 | 통합 빌드와 역할별 테스트 데이터 준비 | P0 케이스 실행, 차단 결함 없음 |
| UAT | 사용 가능한 검증 환경 및 기관 정책 승인 | 업무 담당자 승인과 잔여 결함 합의 |

**결함 심각도:** S1 데이터 노출·손실·핵심 장애, S2 주요 업무 불가/잘못된 상태, S3 기능 일부 제한·우회 가능, S4 표시·문구 문제. 우선순위는 기관 영향과 수정 긴급성으로 별도 지정한다.

**G5 출시 종료 기준:** P0 수용 기준 충족, S1/S2 미해결 결함 없음, 권한·감사·완료 요약 테스트 통과, UAT 승인, 미결정 운영 정책 해결 또는 명시적 승인. 현재는 모두 미판정이다.

## 5. 일정·책임·보고

일정과 담당자는 미정이다. 구현 담당은 자동/단위·통합 검증, QA는 시스템 테스트와 결함 추적, 운영 책임자는 SLA·분류 정책 승인과 UAT를 맡는 것을 제안한다. 실제 담당 지정 전에는 승인으로 간주하지 않는다.

일일 보고에는 실행 케이스, 통과/실패/차단, 신규·해결 결함, 다음 작업을 기록한다. 주간 보고에는 요구사항 커버리지, 심각도별 미해결 결함, 위험·결정 필요 사항을 포함한다. 결함에는 재현 환경, 단계, 기대/실제 결과, 증빙, 영향 ID를 기록한다.

## 6. 위험 및 접근성

| 위험 | 대응 |
|---|---|
| 기관 SLA·권한 규칙 미정 | 가정으로 통과 판정하지 말고 정책 승인 후 케이스 확정 |
| RLS 설정 누락 | 사용자 역할별 긍정/부정 DB 접근 테스트 |
| 감사 이력 부분 저장 | 트랜잭션 실패 주입 테스트 |
| 동시 변경 덮어쓰기 | 예상 상태/버전 불일치 충돌 테스트 |
| 개인정보 포함 테스트 데이터 | 가짜 데이터만 사용, 결과 캡처에서 식별자 제거 |

접근성 점검은 키보드 탐색, 포커스 표시, 입력 라벨·오류 안내, 대비, 색 외 상태 표현, 모바일 화면을 포함한다. 법적 적합성 인증이나 도구 기준은 별도 승인 없이는 단정하지 않는다.
