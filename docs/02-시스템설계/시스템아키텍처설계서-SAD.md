## 1. 목적과 범위
예정 기술인 Next.js, TypeScript, Supabase를 이용한 인증·업무 데이터·권한·화면 구성의 방향을 정의한다. 배포 사업자, 성능·가용성 목표, 기관 연동은 미결정이며 이 문서는 확정 구현 사실이 아니다.

## 2. 아키텍처 개요
### 2.1 스타일 및 원칙
웹 앱과 관리형 Supabase를 결합한 모듈형 모놀리스 구성을 제안한다. 현재 요구사항에 별도 마이크로서비스나 메시지 큐는 필요하지 않다. 사용자 세션과 DB RLS를 함께 사용하고, 상태 변경과 감사 이력은 원자적으로 저장한다.

### 2.2 시스템 컨텍스트
~~~mermaid
flowchart LR
  U[신고자 / 운영자 / 관리자] --> WEB[Next.js 웹 앱]
  WEB --> AUTH[Supabase Auth]
  WEB --> DB[Supabase Postgres + RLS]
  WEB -. P1 첨부 .-> STORAGE[Supabase Storage 비공개]
  DB --> LOG[감사 이력]
~~~

외부 시민 신고, 설비 텔레메트리, 이메일·문자 알림은 v1 범위 밖이다.

### 2.3 컴포넌트 책임
| 영역 | 책임 |
|---|---|
| src/app | 로그인, 대시보드, 신고 목록·상세·작성, 관리자 화면 |
| src/components | 공통 표, 필터, 상태 배지, 폼, 내비게이션 |
| src/lib | 입력 검증, 날짜/SLA 계산, Supabase 클라이언트, 권한 보조 |
| 서버 액션/DB 함수 | 권한 재검증, 상태 전이 및 감사 기록 트랜잭션 |
| Supabase Auth/Postgres | 사용자 인증, 업무 데이터, 관계·제약·RLS |
| Supabase Storage (P1) | 권한 제한 첨부 저장 |

### 2.4 핵심 흐름
신고 생성은 인증 → 입력 검증 → 동일 자산 미해결 신고 안내 → 사용자의 선택에 따른 저장 순서다. 유사 신고는 차단이나 자동 병합을 하지 않는다. 상태 변경은 최신 상태와 권한 확인 후 업무 행과 감사 행을 같은 트랜잭션으로 기록한다. 공개 업데이트와 내부 메모는 별도 접근 정책을 적용한다.

## 3. 기술 구성 제안
| 계층 | 제안 | 미결정 사항 |
|---|---|---|
| 웹 | Next.js App Router, TypeScript | 버전 및 실제 설치 여부 |
| UI | shadcn/ui, Tailwind CSS 검토 | 의존성·컴포넌트 확정 |
| 인증/DB | Supabase Auth, Postgres | 계정 발급 및 역할 저장 설계 |
| 파일 | Supabase Storage (P1) | 형식·크기·보존 기간 |
| 배포 | 미정 | 기관 인프라, CI/CD, 환경 분리 |

서비스 역할 키는 서버 비밀 설정에만 두고 브라우저 번들에 포함하지 않는다. RLS 정책이 화면의 메뉴 표시보다 우선한다.

## 4. 보안·운영
신고자는 본인 신고와 공개 업데이트만 조회한다. 운영자는 전체 업무 신고를 처리하고 관리자는 사용자 역할·자산·지원되는 기준을 관리한다. 파일은 공개 URL을 사용하지 않는다. 오류 응답은 비밀값과 내부 스택을 노출하지 않는다. 개발·검증·운영 환경 분리와 백업·복구 주기는 배포 환경과 기관 정책을 확인한 뒤 확정한다. 임의의 응답시간·업타임 수치는 설정하지 않는다.
