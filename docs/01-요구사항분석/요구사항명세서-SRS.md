## 1. 문서 개요

### 1.1 목적 및 범위

본 문서는 내부 사용자가 공공 시설물·전산 자산 장애를 접수하고, 운영 담당자가 분류·배정·조치하며, 관리자가 처리 현황과 이력을 관제하는 반응형 웹 서비스의 요구사항을 정의한다. 첫 사용 가능 버전(P0)은 인증과 권한, 자산 관리, 장애 접수·처리, 감사 이력, SLA 표시, 대시보드를 포함한다. 첨부·고급 분석·CSV 내보내기는 P1이다.

### 1.2 용어와 우선순위

- **신고:** 장애 또는 이상 현상을 시스템에 등록한 건.
- **조치 기록:** 신고 처리 과정에서 작성한 공개 업데이트 또는 내부 메모.
- **감사 이력:** 상태·기한 등 주요 값이 바뀐 사실, 변경자, 시각을 남긴 기록.
- **P0:** 첫 사용 가능 버전에 필수. **P1:** 이후 개선 후보.
- 기관 정책이 정해지지 않은 값은 승인된 기준이 아니며, 설정 및 미결정 항목으로 다룬다.

### 1.3 참고 자료와 문서 간 기준

PRD가 제품 범위와 수용 기준의 기준이다. 비즈니스 정책서는 운영 규칙, 서비스 기획서는 사용자 가치와 MVP 범위, DESIGN.md는 화면 표현 원칙을 보완한다. 서로 충돌하거나 미정인 기관별 정책은 임의로 확정하지 않고 미결정 항목으로 등록한다.

## 2. 시스템 설명

### 2.1 사용자 유형

| 액터 | 목적 | 권한 범위 |
|---|---|---|
| 신고자 | 신고를 제출하고 본인 건의 진행 상황 확인 | 신고 생성, 본인 신고 및 공개 조치 정보 조회 |
| 운영 담당자 | 신고 분류, 담당자·우선순위·기한 지정 및 조치 | 전체 신고 조회·처리, 공개 업데이트와 내부 메모 작성 |
| 관리자 | 서비스 기준·사용자·자산 운영 | 운영 담당자 권한과 사용자 역할·자산·기준 관리 |

비로그인 사용자는 신고 정보 및 운영 화면에 접근할 수 없다. 역할 권한은 서버와 데이터베이스에서 함께 강제한다.

### 2.2 운영 환경과 제약

예정 구성은 Next.js, TypeScript, Supabase Auth/Postgres/Storage이며 화면은 반응형 웹이다. 실제 배포 환경, 브라우저 지원 범위, 동시 사용자 규모는 미정이다. Supabase 서비스 역할 비밀키는 브라우저 코드에 포함하지 않는다. 공개 시민 신고, 설비 텔레메트리, 자동 탐지, 외부 알림 발송, 휴일·근무시간을 반영한 SLA 산정은 v1 범위 밖이다.

### 3.2 상세 요구사항

#### FR-001: 인증 (P0)

- 시스템은 인증된 사용자의 로그인·로그아웃을 제공해야 한다.
- 비인증 요청은 신고 데이터와 운영 화면에 접근할 수 없어야 한다.
- 계정 발급 및 복구 절차는 기관 계정 운영 방식 확정 전까지 미정으로 둔다.

#### FR-002: 역할 및 인가 (P0)

- 시스템은 각 사용자에게 신고자, 운영 담당자, 관리자 역할 중 하나를 적용해야 한다.
- 신고자는 자신의 신고만 조회할 수 있으며 타인의 상세·첨부·내부 메모를 조회할 수 없어야 한다.
- 운영 담당자는 전체 신고를 조회·처리할 수 있어야 한다.
- 사용자 역할·자산·운영 기준 관리 기능은 관리자에게만 허용해야 한다.
- 권한 검사는 화면 표시 제어에 의존하지 않고 서버 및 데이터 접근 정책에서 수행해야 한다.

#### FR-003: 자산 관리 (P0)

- 관리자는 자산을 등록·수정·비활성화할 수 있어야 한다.
- 신고 입력은 활성 자산 선택을 지원해야 한다.
- 등록되지 않은 위치를 이용한 신고도 허용하고 원문 위치를 보존해야 하며, 운영자가 나중에 자산과 연결할 수 있어야 한다.
- 비활성 자산은 신규 신고 대상 선택에서 제외하되 기존 신고의 참조는 유지해야 한다.

#### FR-004: 신고 생성 (P0)

- 신고 입력 필수값은 자산 또는 위치, 제목, 상세 증상, 우선순위, 발생 시각이어야 한다.
- 시스템은 접수 ID, 신고자, 접수 시각, 초기 상태를 생성해야 한다. 초기 상태는 ‘접수’다.
- 입력 오류 시 필드별 안내를 보여주고, 저장 실패 시 작성 내용을 가능한 범위에서 보존해야 한다.
- 접수 성공 시 신고자는 접수 ID와 현재 상태를 확인할 수 있어야 한다.

#### FR-005: 중복 의심 안내 (P0)

- 시스템은 같은 자산의 미해결 신고가 있을 때 유사 신고 가능성을 안내해야 한다.
- 안내에는 기존 신고를 식별하고 확인할 수 있는 정보만 포함해야 한다.
- 유사 신고 안내는 접수를 자동 차단하거나 신고를 자동 병합해서는 안 된다. 신고자는 별도 건으로 계속 접수할 수 있어야 한다.

#### FR-006: 신고 조회 및 검색 (P0)

- 신고자는 본인 신고 목록과 상세, 공개 가능한 상태·조치 업데이트를 조회할 수 있어야 한다.
- 운영 담당자와 관리자는 권한에 따라 전체 신고를 목록·상세로 조회할 수 있어야 한다.
- 운영 목록은 상태, 우선순위, 자산/위치, 기간 필터와 검색·정렬을 지원해야 한다. 검색 대상 필드는 구현 단계에서 확정한다.
- 목록은 데이터 없음, 로딩, 오류, 필터 결과 없음 상태를 구분해 제공해야 한다.

#### FR-007: 분류 및 배정 (P0)

- 운영 담당자는 신고에 담당자, 우선순위, 처리 기한을 지정·변경할 수 있어야 한다.
- 해당 변경은 변경자와 시각을 포함해 감사 이력에 남아야 한다.
- 우선순위 단계와 신고 유형 분류 목록은 기관 정책 결정 전까지 설정 항목으로 취급한다.

#### FR-008: 조치 기록 (P0)

- 운영 담당자는 신고에 공개 업데이트 또는 내부 메모를 추가할 수 있어야 한다.
- 공개 업데이트는 신고자에게 표시할 수 있어야 하고, 내부 메모는 운영 권한자만 조회할 수 있어야 한다.
- 기록에는 작성자와 작성 시각이 연결되어야 한다.
- 수정·삭제 권한과 보존 기간은 기관 기준이 확정되기 전까지 임의 적용하지 않는다.

#### FR-009: 상태 변경 및 완료 (P0)

- 허용 상태는 ‘접수’, ‘조치 중’, ‘완료’다. 정상 흐름은 접수 → 조치 중 → 완료다.
- 상태 저장 시 서버는 저장 직전의 현재 상태를 확인하고, 동시 변경으로 최신 값이 달라졌다면 덮어쓰지 않아야 한다.
- 완료 처리에는 결과 요약과 완료 시각이 필수다.
- 완료 신고는 일반 사용자가 수정·재개할 수 없어야 한다. PRD에 따라 관리자의 완료 건 수정은 수정 사유를 남기며 허용할 수 있다.
- 완료 후 추가 조치가 필요하면 후속 신고를 생성해 연결한다.

#### FR-010: 감사 이력 (P0)

- 상태 변경은 행위자, 시각, 이전 상태, 새 상태를 기록해야 한다.
- 담당자·우선순위·기한 등 주요 변경도 행위자와 시각, 변경 항목 및 이전·새 값을 기록해야 한다.
- 상태 변경과 그 상태 감사 이력은 하나의 트랜잭션으로 처리해야 한다. 감사 이력 저장 실패 시 상태 변경도 실패해야 한다.
- 감사 이력은 일반 사용자 및 운영 담당자가 임의 수정·삭제할 수 없어야 한다.

#### FR-011: SLA 및 관제 대시보드 (P0)

- 대시보드는 전체 접수, 미처리, SLA 임박, 완료 건수를 표시해야 한다.
- 최근 신고 표는 ID, 제목, 자산/위치, 우선순위, 상태, 담당자, 기한, 최근 변경을 제공해야 한다.
- 미완료 신고의 기한이 현재 시각보다 이전이면 SLA 초과로 계산해야 한다. 완료 건은 미완료 초과 건수에 포함하지 않는다.
- 기한 미지정 신고는 임박·초과로 분류하지 않고 별도로 식별할 수 있어야 한다.
- 임박 기준은 관리자 설정값으로 적용한다. 미설정 시 24시간 이내는 기획 제안값으로 표시하되 기관의 확정 SLA로 표현하지 않는다.
- 화면 시간은 한국 표준시로 표시하고 저장 시각은 시간대 정보를 유지해야 한다. 휴일·근무시간 제외 계산은 지원하지 않는다.

#### FR-012: P1 기능

- 첨부 기능 도입 시 파일 조회는 신고 권한과 동일한 접근 정책을 적용해야 한다.
- 분석은 기간별 접수 추이, 유형별 건수, 평균 처리 시간 및 SLA 준수 현황을 제공할 수 있다.
- CSV 내보내기를 제공할 경우 사용자 권한과 현재 검색·필터 조건을 적용해야 한다.
- P1 세부 정책(파일 형식·용량·보존)은 구현 전에 결정한다.

| NFR-006 반응형 | 모바일 화면에서 신고, 본인 진행 조회, 주요 상태·기한 확인이 가능하다. | 모바일 뷰포트 점검 |
| NFR-007 사용성 | 로딩·빈 결과·오류·정상 데이터를 구분하고 오류 후 복구 행동을 안내한다. | 각 화면 상태 점검 |

성능, 가용성, 동시 사용자 목표는 기관 요구와 배포 조건이 정해지지 않아 본 초안에서 수치를 정하지 않는다.

## 5. 외부 인터페이스와 화면

### 5.1 사용자 인터페이스

주요 화면은 로그인, 운영 대시보드, 신고 작성, 신고 목록, 신고 상세·처리 이력, 자산 관리, 사용자·운영 기준 관리다. 인터페이스는 DESIGN.md의 정보 우선순위, 중립 표면, 텍스트 병행 상태 표시, 반응형 기준을 따른다.

### 5.2 시스템 인터페이스

예정 백엔드는 Supabase Auth와 Postgres다. 데이터 읽기·변경은 사용자 역할과 RLS 정책을 적용한다. 파일 첨부는 P1이며 Supabase Storage 사용 시에도 신고 권한을 확인한다. 외부 알림·모니터링 연동은 범위 밖이다.

| 신고 | 접수 ID, 신고자, 자산 또는 원문 위치, 제목, 증상, 우선순위, 상태, 담당자, 접수·처리기한·완료 시각 |
| 조치 기록 | 신고 ID, 작성자, 공개 범위, 내용, 작성 시각 |
| 감사 이력 | 신고 ID, 행위자, 변경 항목, 이전·새 값, 변경 시각 |
| 후속 신고 연결 | 원 신고 ID, 후속 신고 ID, 연결자, 연결 시각 |

보존·백업·삭제 기간은 기관의 개인정보 및 기록 관리 기준 확인 후 정한다. 일반 사용자는 감사 기록을 수정할 수 없다.

## 7. 검증 및 수용 기준

검증은 기능·권한 테스트와 화면 시나리오 점검으로 수행한다. 핵심 수용 기준은 다음과 같다.

1. 신고 제출 후 ID와 초기 상태를 확인할 수 있다.
2. 같은 자산의 미해결 신고가 있으면 안내를 받고도 계속 접수할 수 있다.
3. 신고자는 타 사용자 신고와 내부 메모에 접근할 수 없다.
4. 상태 변경 시 이력이 함께 저장되며, 이력 저장 실패 시 상태도 변경되지 않는다.
5. 미완료 기한 초과와 완료 건 집계가 구분된다.
6. 운영자는 검색과 다중 필터를 적용해 신고를 찾을 수 있다.
7. 모바일에서 신고와 본인 진행 조회를 완료할 수 있다.

## 8. 미결정 사항

- 기관별 SLA 및 임박 기준과 적용 단위
- 우선순위·유형 분류 체계
- 내부 계정 생성·초대·복구 방식
- 기관별 브라우저·성능·가용성 요구
- 첨부 제한, 데이터 보존·백업 및 개인정보 처리 기준
- 완료 건 수정 권한의 세부 범위와 후속 신고 연결 정책
