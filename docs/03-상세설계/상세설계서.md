# 상세 설계서 (Detailed Design Document)

## 1. 문서 개요

### 목적 및 범위
장애 접수 및 관제 대시보드의 도메인 모델, 업무 흐름, 상태 규칙, 모듈 책임과 검증 조건을 구현 수준으로 정리한다. 구현 전 설계 초안이며 실제 저장소에는 애플리케이션 코드가 아직 없다. 예정 스택은 Next.js, TypeScript, Supabase다. 첨부·분석·내보내기는 P1로 분리한다.

[SRS](../01-요구사항분석/요구사항명세서-SRS.md), [RTM](../01-요구사항분석/요구사항추적매트릭스-RTM.md), [SAD](../02-시스템설계/시스템아키텍처설계서-SAD.md), [DB 설계서](../02-시스템설계/데이터베이스설계서.md), [API 설계서](../02-시스템설계/API설계서.md), [화면 설계서](../02-시스템설계/화면설계서.md), [비즈니스 정책서](../00-기획/비즈니스정책서.md), [DESIGN](../../DESIGN.md).

## 2. 도메인 모델

| 개념 | 핵심 정보 | 책임 및 규칙 |
|---|---|---|
| Profile | id, role, isActive | 인증 사용자와 업무 역할 연결, 자기 역할 변경 금지 |
| Asset | 이름, 관리번호, 유형, 위치, 활성 상태 | 신고에서 선택할 시설·전산 자산 제공 |
| Incident | 신고자, 자산/위치, 제목, 증상, 우선순위, 상태, 담당자, 기한 | 장애의 현재 업무 상태 관리 |
| IncidentUpdate | 신고, 작성자, 공개 범위, 내용, 시각 | 공개 진행 사항 또는 내부 메모 기록 |
| IncidentAuditLog | 행위자, 신고, 변경 항목, 전/후 값, 시각 | 주요 변경 추적 |

신고는 신고자와 연결되며 자산은 선택 사항이다. 자산을 선택하지 않아도 원문 위치를 보존한다. 완료 후 추가 처리가 필요하면 기존 건을 재개하지 않고 후속 신고를 별도로 생성해 연결한다.

### 권장 코드 구조
~~~text
src/
  app/                 화면, 라우트, 서버 액션
  components/          공통 UI
  features/
    incidents/         신고 작성·조회·처리
    assets/            자산 관리
    dashboard/         집계와 관제 목록
    auth/              세션과 역할별 진입
  lib/
    supabase/          서버/브라우저 클라이언트
    validation/        입력 검증
    sla/               임박·초과 계산
    errors/            사용자 오류 변환
supabase/
  migrations/          스키마, RLS, DB 함수
  tests/               권한·업무 규칙 테스트
~~~

실제 파일 구조가 만들어질 때 저장소 AGENTS.md와 프로젝트 설정을 우선한다.

## 3. 시퀀스 설계

### 3.1 장애 신고
~~~mermaid
sequenceDiagram
  actor R as 신고자
  participant UI as 신고 화면
  participant S as 서버 액션
  participant DB as Postgres/RLS
  R->>UI: 신고 필수값 입력
  UI->>S: 접수 요청
  S->>S: 세션과 입력 검증
  S->>DB: 동일 자산의 미해결 신고 조회
  DB-->>UI: 유사 후보 안내(차단 아님)
  R->>UI: 계속 접수 선택
  UI->>S: 생성 확정
  S->>DB: 신고 저장 및 접수 번호 발급
  DB-->>UI: 접수 번호·상태·시각 반환
~~~

기본 중복 안내 기준은 동일 자산의 미완료 신고다. 텍스트 유사도 자동 탐지는 v1에서 하지 않는다. 실제 저장 요청에서도 필수값과 권한을 다시 검사하고 재시도 중 중복 생성을 방지한다.

### 3.2 상태 변경과 이력
~~~mermaid
sequenceDiagram
  actor O as 운영 담당자
  participant UI as 처리 패널
  participant S as 서버 액션
  participant DB as 트랜잭션 함수
  O->>UI: 상태와 결과 입력
  UI->>S: targetStatus, expectedStatus
  S->>DB: 권한 및 최신 상태 확인
  DB->>DB: 업무 행과 감사 이력을 함께 기록
  alt 성공
    DB-->>UI: 갱신 상태
  else 충돌 또는 저장 오류
    DB-->>UI: 변경 미반영 오류
  end
~~~

### 3.3 로그인
로그인 화면에서 Supabase Auth로 인증하고, 서버가 Profile 활성 상태와 역할을 확인한 뒤 허용된 시작 화면으로 이동시킨다. 계정 초대·복구 방식은 기관 결정 전까지 미정이다.

## 4. 상태 및 계산 규칙

~~~mermaid
stateDiagram-v2
  [*] --> 접수
  접수 --> 조치중
  조치중 --> 완료
  접수 --> 완료: 바로 해결한 경우
  완료 --> [*]
~~~

허용 전이는 접수→조치 중, 접수→완료, 조치 중→완료다. 완료 시 결과 요약과 완료 시각이 필수다. 완료 건은 일반적으로 재개하지 않고 후속 신고를 연결한다. 완료 건 수정은 관리자만 가능하며 사유를 감사 이력에 남긴다.

SLA 판정:
1. 기한이 없으면 미설정으로 분류한다.
2. 완료 상태는 미완료 임박·초과 집계에서 제외한다.
3. 미완료이며 현재 시각이 기한을 넘으면 초과다.
4. 그 외 미완료 건 중 남은 시간이 설정 임계값 이내면 임박이다.
5. 초기 24시간은 제안값이며 기관 확정 전 상수로 고정하지 않는다. 휴일·근무시간 보정은 범위 밖이다.

## 5. 모듈 상세 설계

### 인증·권한 모듈
요청 세션을 서버에서 검증하고 Profile의 활성 상태와 역할을 확인한다. 데이터베이스 RLS도 같은 권한 경계를 강제한다. 신고자는 본인 신고와 공개 업데이트만 조회한다. 운영 담당자는 신고를 처리하고 관리자는 역할·자산·지원되는 기준을 관리한다. 클라이언트가 전송한 역할값은 신뢰하지 않는다.

### 신고 모듈
생성 요청은 assetId 또는 위치, title, description, priority, occurredAt을 받는다. reporterId, incidentNumber, 접수 시각, 초기 상태는 서버가 결정한다. 유사 신고 발견은 안내만 하며 자동 병합·접수 차단에 사용하지 않는다. 담당자·기한·상태 변경은 최신 버전/상태를 확인한 서버 처리 경로를 거친다.

### 조치 기록·감사 모듈
조치 기록은 작성자와 public/internal 공개 범위를 저장한다. 신고자 응답에는 공개 기록만 포함한다. 상태·담당자·우선순위·기한 변경은 변경자, 시각, 항목, 이전·새 값을 기록한다. 상태 변경과 감사 로그는 단일 DB 트랜잭션으로 저장하며 한쪽 실패 시 모두 롤백한다.

### 자산·대시보드 모듈
자산 쓰기는 관리자만 허용한다. 비활성화해도 기존 신고 참조를 보존한다. 대시보드는 권한 범위를 먼저 적용한 뒤 동일한 SLA 규칙으로 집계한다. 목록 검색·필터는 서버/DB에서 수행하며 데이터 없음·로딩·오류 상태를 구분한다.

### 첨부 모듈 (P1)
승인 시 비공개 Storage에 업로드하고 신고 접근 권한을 매번 확인한다. 허용 형식, 크기, 보존 기간 결정 전에는 구현하지 않는다.

## 6. 오류와 동시성

| 상황 | 처리 |
|---|---|
| 입력 검증 실패 | 필드별 안내, 저장하지 않음 |
| 인증·권한 실패 | 데이터 노출 없이 접근 거부 |
| 상태 충돌 | 최신 상태 안내, 덮어쓰기 금지 |
| 감사 로그 저장 실패 | 업무 변경도 롤백 |
| 네트워크 실패 | 성공으로 표시하지 않고 재시도 제공 |
| 재전송 | 서버 측 중복 생성 방지 |

## 7. 코딩 및 리뷰 기준
컴포넌트는 PascalCase, 함수·변수는 camelCase, 상수는 UPPER_SNAKE_CASE를 사용한다. DB 테이블·컬럼은 설계서의 snake_case를 따른다. 권한과 업무 규칙은 서버/DB에서 최종 검증한다. 단일 기능에 과한 범용 추상화를 추가하지 않는다. 리뷰에서는 요구사항 ID, RLS, 원자적 감사 이력, 개인정보 노출, 오류 상태와 테스트를 확인한다.
