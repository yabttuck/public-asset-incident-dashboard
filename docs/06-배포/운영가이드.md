# 운영 가이드 (Operations Guide)

## 1. 시스템 개요
본 프로젝트는 장애 접수, 담당자 배정, 처리 상태 및 기한을 관리하는 내부 웹 서비스다. 예정 구성은 Next.js, Supabase Auth, Supabase Postgres이며 첨부는 P1이다. 현재 운영 시스템과 배포 주소는 없다. 본 문서는 향후 운영 인수 전 완성해야 할 초안이다.

## 2. 접속 및 비밀정보
운영 URL, Supabase 프로젝트, 관리 콘솔과 접근 담당자는 환경 구축 후 별도 승인된 비밀 저장소/접근 관리 문서에 기록한다. 이 가이드와 공개 Git에는 비밀번호, 토큰, 서비스 역할 키를 기재하지 않는다. 관리자 접근은 업무상 필요한 인원에게만 부여하고 퇴직·보직 변경 시 회수한다.

## 3. 모니터링
모니터링 제품, 지표 임계값, 알림 채널은 미정이다. 운영 시작 전에 아래를 정하고 담당자를 지정한다.

| 영역 | 점검 항목 |
|---|---|
| 웹 앱 | 배포 상태, 오류율·응답 이상, 로그인 및 주요 경로 |
| 인증 | 인증 실패 급증, 세션·계정 문제 |
| 데이터베이스 | 연결·쿼리 오류, 저장 실패, RLS 정책 변경 |
| 업무 데이터 | 접수량, 미처리·기한 임박·초과, 완료·감사 로그 일관성 |
| 보안 | 권한 이상, 비밀값 노출 여부, 관리자 변경 기록 |

측정하지 않은 정상 범위나 가용성 보장은 기입하지 않는다. 내부 메모와 상세 신고 본문은 일반 로그나 알림에 남기지 않는다.

## 4. 장애 대응 절차

### 4.1 공통 대응
1. 신고 또는 모니터링으로 장애를 확인하고 발견 시각·영향 범위를 기록한다.
2. 서비스 장애와 개별 업무 신고를 구분하고 S1~S4 심각도를 지정한다.
3. 개인정보 노출 우려가 있으면 접근을 제한하고 보안 책임자에게 즉시 전달한다.
4. 안전한 완화 조치를 적용하고 담당자에게 상황을 공유한다.
5. 로그인, 신고 저장, 처리 상태, 감사 이력을 점검한다.
6. 원인·영향·조치·후속 과제를 기록하고 필요하면 사후 검토한다.

내부 연락처·온콜 일정·에스컬레이션 담당은 운영 조직 지정 전까지 미정이다.

### 4.2 주요 시나리오별 초동 조치
| 시나리오 | 초동 조치 |
|---|---|
| 앱 응답 없음 | 배포 상태와 로그 확인, 최근 릴리스 식별, 승인된 이전 버전 복구 판단 |
| 로그인 실패 | Auth 상태와 환경 설정 확인, 키를 채팅/이슈에 복사하지 않고 비밀 관리 경로에서 교체 여부 검토 |
| DB 저장 실패 | 오류 범위와 DB 상태 확인, 상태/감사 데이터가 부분 저장됐는지 조사 |
| 상태·감사 불일치 의심 | 추가 변경을 제한하고 원본 이력 보존, DB 트랜잭션 및 로그 점검 |
| RLS/데이터 노출 의심 | 관련 접근을 차단·제한하고 보안 담당자에게 통보, 감사 자료 보존 |
| SSL/도메인 오류 | 인증서·도메인 제공자 상태를 확인하고 승인된 갱신 절차 수행 |

운영 DB를 직접 수정하거나 로그를 삭제해 문제를 숨기지 않는다. 수동 데이터 정정은 승인, 백업 확인, 사유·행위자 기록 후 수행한다.

## 5. 백업 및 복구
백업 주기·보존 기간·복구 목표·책임자는 Supabase 요금제와 기관 기록 정책 확인 후 확정한다. 운영 시작 전에 백업 기능과 복구 절차를 검증하고 복구 연습 결과를 기록한다. 복구 시점 이후 데이터 손실 범위를 확인하고 담당 승인 없이 운영 데이터를 덮어쓰지 않는다.

## 6. 정기 작업
- 일일: 오류·로그인 상태, 미처리/초과 신고, 백업 경고 점검
- 주간: 관리자 계정과 역할, 이상한 접근·변경, 실패 저장 추세 확인
- 월간: 복구 가능성, 계정 권한 회수, 의존성·인증서 갱신 일정 검토
- 주기 미정: 실제 운영 요구와 담당 인력을 고려해 체크 주기를 승인

## 7. 운영 인수 전 필수 기입
운영 주소, 담당 조직·연락망, 모니터링 링크와 경보 기준, 백업/복구 절차, 데이터 보존 기준, 기관 SLA, 긴급 변경 승인 절차를 지정한다. 실제 운영 기록과 개인 연락처는 공개 저장소에 게시하지 않는다.
